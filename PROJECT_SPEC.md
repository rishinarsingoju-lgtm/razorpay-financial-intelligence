# PROJECT_SPEC.md

## Project
AI-augmented financial reconciliation MVP for Razorpay Buildathon. Deterministic engine establishes financial truth (matching, calculations, exception detection). One Gemini agent explains/investigates via tool calls — never calculates, never is the source of truth.

Chain: **Order → Payment → Refund/Fee → Settlement → Settlement Item → Bank Credit**

## Stack
- Frontend: Next.js, TypeScript, Tailwind, shadcn/ui
- Backend: Python, FastAPI, SQLAlchemy, PostgreSQL
- AI: Gemini API (single agent, function-calling)
- Data source: Razorpay Test API (orders/payments/refunds) + synthetic generator (settlements/settlement_items/bank_transactions, seeded RNG)
- UI reference: `stitch_fintech_operations_design_system/` — use as visual/component reference for frontend build

## Core Principle
Deterministic Python code = financial truth (matching, math, status, DB writes).
AI agent = investigation, explanation, natural language only.
Agent tools and REST API endpoints must call the **same underlying service-layer functions** — UI numbers and AI-quoted numbers must never diverge.

## Database Entities

**orders** — id, razorpay_order_id, amount, currency, status, receipt, created_at

**payments** — id, razorpay_payment_id, order_id (FK), amount, fee, tax, status, method, created_at, reconciliation_status (derived)

**refunds** — id, razorpay_refund_id, payment_id (FK), amount, status, created_at

**fees** — id, payment_id (FK), type (gateway_fee/gst/other), amount [synthetic if not in Razorpay test response]

**settlements** — id, razorpay_settlement_id (nullable), amount, status (processed/processing/on_hold), expected_date, processed_date (nullable), created_at [synthetic]

**settlement_items** — id, settlement_id (FK), payment_id (FK, nullable), refund_id (FK, nullable), amount (signed), entry_type (payment/refund/fee_deduction) [synthetic]

**bank_transactions** — id, settlement_id (FK, nullable), amount, credited_date (nullable), bank_reference [synthetic]

**reconciliation_exceptions** — id, type, severity, related_order_id/payment_id/settlement_id (nullable FKs), expected_amount, actual_amount, discrepancy, description, status (open/investigating/resolved), detected_at [derived]

Field source tags: Razorpay = real API data. Synthetic = generated by seeder. Derived = computed by reconciliation engine.

## Financial Calculations (deterministic)
- **Expected amount** = payment.amount − Σrefunds.amount − fees.amount
- **Settled amount** = Σsettlement_items.amount for the batch containing that payment
- **Bank-received amount** = bank_transactions.amount where credited_date is not null
- **Discrepancy** = expected − settled (payment level); settled − bank-received (settlement level)
- **Status derivation**: pending (not yet in a settlement) → processing (in batch, expected_date not passed) → delayed (expected_date passed, still processing) → settled (processed + bank credit matched) → held (status=on_hold)

## Reconciliation Matching Hierarchy (in order)
1. Exact match: payment_id FK in settlement_item + amount matches → `matched`
2. Fallback match: no FK, but same amount+date range unclaimed → `fallback_matched` (flag for review)
3. Partial: Σsettlement_items < expected_amount → `partially_matched`
4. Duplicate: ≥2 settlement_items with same payment_id, entry_type=payment → `duplicate_flagged`
5. Missing: no settlement_item + today > expected_date → `missing`
6. Fee mismatch: fee_deduction settlement_item ≠ fees.amount → `fee_mismatch`
7. Bank mismatch: settlement processed but bank_transactions.amount ≠ settlement.amount or missing → `bank_mismatch`

## Exception Types (all deterministic detection)
| Type | Detection |
|---|---|
| delayed_settlement | status=processing AND today > expected_date |
| missing_settlement | no settlement_item AND today > expected_date |
| partial_settlement | Σsettlement_items < expected_amount |
| duplicate | ≥2 settlement_items same payment_id, entry_type=payment |
| fee_mismatch | fee_deduction item ≠ fees.amount |
| bank_credit_mismatch | settlement processed, bank_transactions.amount mismatch or missing |
| unusual_pattern (soft insight, not blocking exception) | refund/delay count > 2x trailing 7-day avg |

## AI Agent

**Model:** single Gemini agent. No multi-agent orchestration in MVP.

**System behavior:** Must call a tool before stating any financial figure. Never estimate or perform its own arithmetic on raw numbers. Cite specific record IDs (exception/payment/settlement) in every answer. If a tool returns empty, say so explicitly — never fabricate.

**Tools (exact names, no additional tools):**
1. `query_transactions(filters: amount_min?, amount_max?, status?, date_from?, date_to?, unmatched_only?)` — find candidate transactions
2. `get_exceptions(filters: type?, severity?, date_from?, date_to?, status?)` — list exceptions
3. `get_settlement_status(settlement_id? | date_range?)` — settlement-level health
4. `compare_periods(period_a, period_b)` — aggregate totals + delta between two date ranges
5. `trace_transaction_chain(payment_id | order_id)` — full order→payment→refund→settlement→bank chain with break point

**Common sequences:**
- "Why is today's settlement lower?" → `compare_periods` → `get_exceptions`
- "Where is the missing ₹X?" → `query_transactions` → `trace_transaction_chain`

## API Endpoints (frontend-facing)
- GET `/api/dashboard/summary`
- GET `/api/transactions` (filterable)
- GET `/api/transactions/{payment_id}/chain`
- GET `/api/exceptions` (filterable)
- PATCH `/api/exceptions/{id}` (status update)
- GET `/api/settlements`
- GET `/api/settlements/{id}`
- POST `/api/copilot/ask` — body `{question}` → `{answer, tool_calls_made, referenced_ids}`
- POST `/api/admin/seed` (dev-only)
- POST `/api/admin/reconcile` (dev-only)

Agent tools are internal Python functions, not separate public routes. Both endpoints and tools call shared service-layer functions.

## Synthetic Data Requirements
- ~15-20 real orders/payments (+4-5 refunds) via Razorpay Test API
- Synthetic settlements/settlement_items/bank_transactions layered on top, shaped to mirror Razorpay's real settlement schema fields
- Seeded RNG (fixed seed, e.g. `--seed 42`) for reproducibility across demo runs
- Exactly one injected instance of each: delayed settlement, missing settlement (must include one exactly ₹50,000 missing case), partial settlement, duplicate, fee mismatch, bank-credit mismatch
- Remainder of records (~14) fully clean/matched for dashboard contrast

**Unverified assumption (spike Day 1):** Razorpay Test Mode Settlement API may return no real data since there's no live bank cycle in test mode. If confirmed empty, settlements/settlement_items/bank_transactions are entirely synthetic — orders/payments/refunds remain real Razorpay data.

## Build Order
1. Schema + migrations (8 tables, FKs, indexes)
2. Razorpay Test API integration spike (confirm settlement API behavior)
3. Seeder: real data (orders/payments/refunds via Razorpay)
4. Seeder: synthetic layer (settlements/items/bank_transactions + 7 injected anomalies)
5. Reconciliation engine (matching hierarchy, writes reconciliation_status)
6. Exception detector (writes reconciliation_exceptions)
7. Financial intelligence functions (summary/comparison aggregation)
8. FastAPI endpoints (test independently before frontend)
9. Agent tool layer (wrap service functions, test in isolation)
10. Gemini agent wiring (system prompt + function-calling + /api/copilot/ask)
11. Frontend: Dashboard, Exceptions, Settlement screens
12. Frontend: Chain Detail, Copilot UI
13. Demo rehearsal + seed data sanity check

## Constraints
- Never commit `.env`; provide `.env.example` with blank values
- Env vars: `DATABASE_URL`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `GEMINI_API_KEY`
- Razorpay Test Mode keys only
- No auth for MVP (single-tenant localhost demo); gate `/api/admin/*` if deployed anywhere reachable
- Agent must never trigger writes — reconciliation runs via `/api/admin/reconcile`, not via a tool
- Same seed must always produce identical exception set (reproducibility requirement)
